> 日期：2026-11-05（America/Los_Angeles）。审查对象：main `12e3d92`、PR #11（`8c8f76e`，含运营手册与 10 张目标机实拍截图）、Issue #12、PR #13（`9c85123`）。

> 方法：阅读截图、运营手册和前端代码；在 main 上用编辑门（`evaluateDraft`）做最小复现。没有访问目标机，没有调用模型。

> 读者：用户（第 0、4 节）；GPT 开发执行（第 1–3、5 节）。本文件是 v3 计划 R1 的补充任务书，不改变 D1–D18。

## 0. 结论

1. **现在的工作流，人走不完。** 第一篇（MiP 解释文）在成稿时被 16 处 D1 BLOCK 拦下。这时界面只提供“下载任务 / 导入结果”（给 Agent 用的入口），运营在页面上没有办法修改并继续。手册也停在这里，写的是“云端修现有结果”。
2. **这 16 处 BLOCK 很可能大多是误报。** 复现结果：中文审稿写“晶台称其 MiP 封装尺寸为 0.65 mm”会触发 BLOCK，写“晶台光电称…”或“Kinglight 称…”则不会。原因是身份词典里 Kinglight 只登记了“Kinglight、晶台光电”，没有常用简称“晶台”。更大的缺口是：16 个 LED 信源中有 11 个没有 owner_entity_id，ENTITIES 里也没有卡莱特、集创北方、创联、巨能、灰度、OAAA、LEDinside；复现中“卡莱特称 Z6 刷新率为 3840Hz”同样被 BLOCK。也就是说，这些信源的每一篇中文审稿都会被大量误拦。
3. **界面把机器的编码直接给人看。** 触发字母（A–E）、规则编号（D1、W2）、BLOCK/WARN、KEEP/HOLD/SKIP、字段路径（drafts[0].review_zh）、字符位置（427–434）、任务 UUID、UTC 时间戳。“D”在系统里有三种意思：新闻类卡片、内容规则 D1（归属）、Grill 决议 D1–D18。
4. **日期显示直接导致了事实错误。** 卡片显示“原日期：2026-10-22T16:00:00.000Z”，而原文是北京时间 10 月 23 日；成稿也写成了 October 22。
5. **运营手册其实是 R1 的操作记录。** 里面有提交哈希、任务 ID、token 数、WorkBuddy 持有器编号和“转云端”等内容，适合交接，不适合一个第一次使用的运营人员照着做。手册也没有写到批准、导出、发布和社媒。
6. **Issue #12 的方向对，但时机和范围不对。** 建议保留 Issue、收窄范围、PR #13 暂不合并（见第 3 节）。当前最该做的是让人能走完第一篇。

## 2. 本回合任务（R1.5“让人能走完第一篇”，GPT 一个长回合）

按顺序做，每项一个提交，回合结束开一个 PR：

1. **R1：身份词典与信源主体。** 先列出建议补充的简称和主体，交给用户确认后再写入 industry/taxonomy.ts 和 sources.json。测试：“晶台称…”“卡莱特称…”“集创北方称…”不再触发 D1 BLOCK，没有归属的数值仍然 BLOCK。
2. **重新检查已保存的 MiP 回复：** 用新词典对原响应重跑编辑门，不调用模型，并报告剩余的 BLOCK 和 WARN 数量与内容。
3. **R2：被拦候选可在页面上修改。** 验收：在 1440 和 390 两个宽度下，运营不下载任何文件，就能把被拦的候选改到没有 BLOCK、保存为稿件，进入正常审稿。
4. **R3：日期按原文日历日期显示，并传给写作。** 验收：2026-10-22T16:00Z 在卡片、任务、稿件上都显示为 2026-10-23（北京时间）；写作输入里带有本地日期。
5. **R4、R5、R7、R8、R9：界面用语。** 以截图前后对比验收；不改审核规则本身。
6. **R6：命中词与低置信度。** 用 ViewSonic 那条真实素材做回归测试。
7. **R10、R11、R12：入口与文档。** 运营手册写到“批准→导出→（用户决定）发布→社媒”，附术语表和“被拦了怎么办”。
8. **把第一篇走完：** 用修好的流程处理 MiP 稿，走到批准和导出；是否发布由用户决定。
9. **冷启动验收：** 用户本人照着新手册，独立把一张卡走到导出，记录卡住的地方。卡住的点修好之后，R1 才算完成。

停止条件沿用 v3 第 4.2 节。另外，第 1 项的名单需要用户确认，第 8 项的发布由用户决定。

## 3. Issue #12 与 PR #13 审查

**认同的部分：** 供应链资料和时讯的价值标准确实不同；同一来源和同一原文只存一份、用途分别判断；首次导入不当新闻；不另建采集器。这些原则正确。

**不建议现在照 Issue 实施的原因：**

1. **没有资料来源，配置就是空的。** 现有 LED 信源都是新闻列表或下载页；规格书、PCN、手册还没有采集入口。PR #13 的设计也写明“生产采集入口未核；现有明纬新闻源不能冒充规格书源”。先有资料入口（R2 的 B1、B3：页面登记、实机和资料录入，可以人工上传 PDF 或产品页），用途配置才有对象。
2. **关键行为大多已经有了：** 版本源首次导入只记基线（R1-0）；新闻卡只认 7 天内；E 卡不会变成 D 卡；旧资料可以作为证据绑定；解释文允许使用旧资料（D4）。Issue 里的验收项，需要先逐条对照现有行为，只补真正缺的部分。
3. **范围过大：** 每个用途各有开关、优先级、周期、回补、审核状态和去向，外加用途判断表、跨来源参数冲突检测、实体型号版本登记。这相当于一个新的知识库，与 AGENTS.md“只定义正在使用的抽象”“开关先要有证据”相冲突，也会给已经难读的界面再加一层概念。
4. **时机：** 第一篇还没走完，误拦问题还没修。PR #13 新增 2,156 行，没有接入任何运行路径（34×2 条全部 UNKNOWN、停用），合并后也只是没有使用者的配置和代码。

**建议：**

- **处理方式：** 保留 Issue #12 但收窄；PR #13 不合并，设计文档保留在分支上供以后参考。
- **R2 里的最小一步（届时再做）：** 每个信源加一个用途字段：时讯 / 资料 / 兼用 / 待确认，默认“待确认”，行为与现在相同。只加一条路由规则：“资料”信源不出新闻卡。信源页可以按用途筛选。
- **以后再说：** 每用途的优先级、周期和审核表，等资料来源真实运行、出现了具体冲突以后再加。“跨来源参数冲突待核”需要结构化抽取参数，单独开 Issue。
