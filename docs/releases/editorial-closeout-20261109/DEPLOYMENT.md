3. 在用户控制位置备份原源码、数据库、附件和配置。不得将 `.env`、公司黑名单或原数据库传入GitHub/公共封包。使用既有备份方式，不新造凭据。
4. 在新暂存目录合入本包源码，保留用户独有改动、`.env`、`runtime/studio.env`、runtime、CAMOS运行时、附件和数据卷。示例配置不覆盖私有文件。本轮无数据库迁移。
5. 用原环境 Node >=24.22.1 安装锁定依赖，执行 `npm ci`、`npm run typecheck`、`npm run build -w @aihot/web`。不要跨Windows/Linux复制node_modules。保留原端口与本机访问限制。
6. 使用既有启动器启动API、SSR Web和Studio worker。新增队列为 `studio.brief`，未启动worker会显示排队。不要执行全量seed，不清表、不删卷、不打开全自动采集或发布。
7. 比对升级前后所有稿件与私有配置；只能在后续明确审稿操作后改变相关稿件版本。本轮把配图/短讯元信息纳入批准哈希，旧批准可能需要重新确认，这是一次明确审稿动作，不应伪造兼容旧批准。

## 五项验收

| 项目 | 操作与有效证据 |
|---|---|
| 保存 | 私人测试稿加入一个BLOCK，修改另一处并保存；重新加载后文字与版本保留，未批准/交付。 |
| 6098 | 复用已有单段稿，不重生成。核对85个保留段及实际改动，以现场数据为准；默认推独立draft ID，读回6098仍publish，原URL、正文其余段和公开标题不变。 |
| 短讯 | 每源记录条数、日期率、正文率、失败原因、结论；选5–12条，去重后≥5个事件；返回1篇in_review、每事件出处/日期、3条速览，WP写入为0。获批准后才推WP草稿。 |
| 审稿 | 先看原句与建议，再采纳。英文替换，中文标旧，剩余问题不隐去。普通风险复核与工程师署名只认实际记录。 |
| 时效 | 20日内上游新品可推荐，20日市场项目不可作为短讯；参考资料不按新闻窗口拦长文。不得用厂商品牌推断窗口或把发现日当发布日。 |

配图预览与上传均可失败；需要浏览器的渲染遇到权限拒绝即停，不换路径绕过。装饰图ALT可以为空；独立信息图需要描述实际内容，不给共享附件反复写入文章关键词。

## 原页覆盖边界

默认交付是独立影子draft，重复推送复用它，绝不把6098改成draft。不可在WP直接发布影子稿。公开标题不带内部 `[UPDATE]`。

可选的单段覆盖API需要显式 `confirm_update`（目标post ID与基线hash）、已绑定原始HTML及片段计划、两次原页读回匹配、明确一键上线授权。正文以现行原始HTML为底只替换计划段落，保持publish；不改其他段、标题、URL或分类。出现差异只保留影子稿。

原生WP读回再写入不提供原子条件更新，仍有并发编辑竞态。执行窗口内应避免其他编辑者同时改同页；没有互斥条件时继续走影子预览和人工更新。WP Revision依赖站点设置及实际写入，本包不承诺必定产生可回滚revision。失败不能把已发布原页降级，未知写入结果不能自动重试覆盖。
