# AIHOT 产品PRD v1.0｜独立采编、内容更新与Blog交付

日期：2026-11-02 America/Los_Angeles。负责人：Codex主策与工程执行；WorkBuddy目标端部署与运行；Opus关键产品设计审查。状态：供审查的PRD；用户已定方向与本文件建议分开标明。

## 0. 产品判断

**当前AIHOT是有素材和审核状态的采编工作台，已经超出定时检索，但尚无证据证明值得持续大量消耗token。** 已有价值是留存来源、绑定版本、调用与结果复用、中文审稿、英文交付、人工批准；主要欠缺是跨日判断增量、决定新写还是更新已有页面、从实际Blog结果学习。不能用健康检查、测试数量、文件数量或出稿字数代替这些业务结果。

建议产品主线：**选题 → 证据变化 → 内容动作 → 审核 → Blog交付 → 结果回看。** 调度只决定什么时候启动；Studio负责每一步用什么证据、是否值得继续、结果放到哪个现有内容位置。无需先重建通用聊天Agent平台。

与一个强基线比较：定时抓源/检索 + 保存上一期摘要 + 同一DeepSeek模型写作 + 人工发布。不能故意用“完全无历史、无规则”的弱定时任务证明AIHOT有价值。AIHOT应在同等内容质量下减少人工操作，或发现基线遗漏的更新机会；做不到应停止扩建。

## 1. 用户已经确定的方向

1. Chipshow Blog子目录；英文对外，中文仅内部审稿。
2. IC、灯珠/封装、箱体、电源、控制系统等多方向；不限户外用电专题。
3. Studio部署到另一台电脑，自身调用OpenCode供应的`deepseek-v4.1-flash`；正常采编不依赖Codex/WorkBuddy替写，也不依赖其聊天窗口。人工仍负责编辑批准。
4. 短讯强调真实时效；技术解释文允许使用较旧但仍有效的资料，按选题采编。没有新鲜消息时允许不发短讯。
5. 允许未证实消息，标题、摘要、正文共同保留限定、来源与日期；后续确认/否认/更正要能更新。
6. D1–D10/W1–W8和逐项确认保留。BLOCK不能人工放行，未知判断只能WARN。≤5问题只作减负愿望，不能作放行条件。
7. CAMOS方法与事实隔离，采用ID可追溯；不注入`data/business`，不把建库日当资料时效。
8. 本轮不处理8080网关或DSH旧密钥；不切换到DeepSeek Pro；不为Opus安排日常写作。

## 3. AIHOT在定时任务之外应承担什么

| 行动 | 简单调度也能做到吗 | AIHOT当前/应有增量 |
|---|---|---|
| 到点检索并写摘要 | 能 | 不作为持续投入理由 |
| 来源、正文、日期留存 | 能用脚本实现 | 当前已集中管理，避免人反复补齐与传文件 |
| 可靠恢复一次成稿 | 可以额外开发 | 当前任务+回执复用已有，失败结果未知不盲重买 |
| 今天与昨天有何不同 | 保存摘要也能部分做到 | 应给出具体主张变化、旧依据、新依据与影响；目前欠缺 |
| 新写/更新旧文/参考/不做 | 可以提示模型建议 | 应关联实际已有页面并让运营一键接续，减少重复页面；目前欠缺 |
| 编辑到官网准确版本 | 可以拼装 | 当前批准与导出已有，发布回读和变更回写待补 |
| 是否省人、值得继续 | 调度本身不回答 | 用真实稿件的人工耗时、采纳和发布结果决定投入 |

目标不是实现只有AIHOT才能做的算法，而是用一个稳定流程替代一组由运营手工拼接、每次都需解释上下文的动作。

## 4. 目标体验与最小对象关系（设计建议）

运营打开现有Studio，先看到“今日值得处理”的建议，而非先在170条原始素材中逐条找。每条建议用四行讲清：**变化是什么、证据在哪、为什么值得处理、建议做什么。** 没有新增价值可显示“暂无新增选题，保留原计划”。这块是拟建界面，不冒充已上线。

已有对象继续使用：`sources → articles/正文版本 → studio_tasks/receipts → studio_drafts/审稿 → Blog页面`。在任务/稿件元数据中按需关联选题、内容动作、对照的已有页面与证据差异；页面URL必须来自实际读取，未知留空。优先衍生查询或缓存，不新增另一套人工维护事实库。是否需要独立事件对象，由Opus在最小变更原则下审查，不预设“事件唯一编辑单位”。

内容动作建议为：新短讯、解释文、更新已有页面、仅留参考、HOLD、SKIP。它们是编辑动作，不替代现有任务waiting/received/blocked和稿件draft/in_review/approved状态，也不解除KEEP/HOLD/SKIP规则。没有匹配到既有采购问题不能直接淘汰有价值行业消息。

## 5. 两种内容产品

### A. 行业短讯

回答谁在何时发布了什么、改变了什么、目前证据能支持到哪里。原始发布日期、发现日期、编辑日期分开；不拿发现旧文时间当新闻时间。初始“新鲜候选”窗口建议7天，作为可调编辑建议交Opus审查；超窗可做明确标日期的回顾，不伪称当日/首发。不强制日更配额。

正文可短，不强制H2/FAQ或统一字数。需要直达来源、事实对象、条件和限定。单源厂商报道如实标示；有公共价值的资讯可以成立，不强塞产品入口或采购问题。

### B. 技术解释与比较

围绕一个真实行业/应用问题组织证据，例如驱动IC扫描与适配、灯珠与屏体指标区别、箱体维护结构、供电效率条件。旧资料在仍适用时可用；说明资料时间与版本，比较时统一测试对象和口径，缺证据就缩小结论。

按问题选择小标题、对比表、直接结论和必要问答；结构服务阅读，不凑模块。应比原厂改写多出适用范围、边界或可靠的多源解释。优先更新已有能承接问题的文章；无对应页面也可新建。

Google说明AI搜索沿用SEO基础，无额外专用优化要求；有帮助、有独特价值的内容比模板堆砌重要。H2、FAQ和长文并非GEO资格证。[AI功能说明](https://developers.google.com/search/docs/appearance/ai-features)、[以人为本内容](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)。本PRD不把Schema、更新频率或发布成功当作排名/AI引用保证。

### 6.1 旧文处理不宜全局“一刀切6个月”

当前`initialBackfillMonths`是首次回填窗口；抓到时日期未知的条目可先通过，之后补正文才暴露旧日期。因此填6不等于默认列表只显示半年内，也不等于所有旧文永不入库。应在补齐后重新分类，分“新鲜候选/待核日期/技术参考”，默认编辑队列看前两类、参考入口仍可检索。不要删除历史库来制造干净列表。

### 6.2 供应商事实与产品选择

用户选择OpenCode供应Flash；WorkBuddy报告成功；[供应商当前Go文档](https://opencode.ai/v2/docs/console/go/)仍描述编码Agent流量和稳定会话要求。三者分开记录。Studio不新增新闻用途预拦截，不伪装编码流量，不因请求成功宣称供应商承诺长期支持；真实拒绝和限流按原回执处理。保留已有Custom接口能力即可，本轮不增加供应商管理平台或探测旧密钥。

## 7. Token投入原则

1. 日期、来源完整性、URL/正文hash重复可确定时，用程序先处理，不为每条旧文先调用模型。
2. 先用有限来源/选题判断值得处理的候选，再只为选中的动作写稿；同一次评估可允许零稿。对已完成任务与未变正文复用已有结果。
3. CAMOS的30,226字符不等于30,226 token，也不证明全部无用。拟按选题取相关规则，保留核心纠错与引用ID；不反复塞全部知识和上轮交接报告。引用裁剪不得丢掉数值条件或将片段冒充完整来源。
4. 已有回执、预算和未知结果机制优先复用；不加无限重试。超时增加至300秒不保证长稿质量，也不授权超时后重复扣费。
5. Opus只做一次聚焦设计审查，默认先读约千字短简报；PRD、证据和源码按问题展开，不调用它读整仓或逐稿润色。Codex落实审查结论。

度量：每篇获准交付的token消耗 = 当批所有成功、失败、重试和弃稿消耗 ÷ 获准交付稿件数。另列人工分钟/篇、可用稿比例与总运营费用。配额型渠道记录实际额度/账单口径；供应商未回报的费用留未知，不能由响应cost=0推导免费。

## 8. 离产出有多远：按结果回答

- **自动产出一篇短讯文件：** WorkBuddy报告已实现，本地文件支持“已有稿件”，本轮未重跑真实模型。
- **一篇可以放心作为当前资讯发布的稿：** 还需真实新鲜来源、主张/参数对象与时区核实、人工批准及Blog落地。当前MiP不因零汉字或无BLOCK自动达到此标准。
- **一篇回答具体问题的技术文章：** 采编与审稿能力已具备基础；还需一次按选题取证、超出改写的解释、相关已有页面对照及发布回读。不是单纯增加H2/FAQ。
- **稳定独立采编服务：** 尚差独立进程托管/调度、跨日增量与内容动作、目标机器验收及成本观察。按缺口推进，不报无依据的完成百分比或固定上线日期。

## 9. 最小试产：先证明值得继续

使用有限真实选题，跑5类输入：新鲜可报道材料、较旧但有技术价值材料、已有页面可更新材料、重复材料、正文/证据不足材料。期望覆盖短讯、解释文、旧文更新三个交付，以及重复/证据不足时不强行出稿。覆盖IC、灯珠、电源等已有条件方向，箱体与控制方向缺资料时如实HOLD。

同一模型、相同可得资料、相近人工熟悉度，对照“定时检索+历史摘要+人工发布”。记录每件输入的最终动作、错误/遗漏、实质修改、人工分钟、总usage与是否真实发布。样本少只能决定下一步工程投入，不能宣布SEO因果收益或触发自动审稿降档。

继续条件：同等事实质量下，至少有清楚可解释的人工节省或有价值更新机会增量，且单位交付成本可接受。若五类样本只证明“又生成一批改写”，暂停扩建跨日平台与看板，保留已可用采编/审稿工具，采用轻量调度。编辑工时与每篇成本的数值目标待首次基线实测后确定，不先编ROI。

30→20→10仍沿用用户原连续样本、漏检和介入率条件；本试产不替代其10/20篇要求。重大事实错误照原规则退档。

## 10. 范围与分期

当前先做：F01–F07最小可试产版本，Opus审查后按依赖细化执行；可先人工发布回读，再自动化CMS。P1在试产说明价值后推进。

本期不做：通用多Agent编排平台、全网新闻覆盖、强制日报数量、全库知识图谱、自动外发发布、自动降审、另一套CRM/事实数据库、以FAQ/文章字数验收GEO、未核实品牌/客户的事实补写。

角色：Studio后端做采编执行；运营选题与逐篇批准；WorkBuddy目标端部署及真实样本回执；Codex主策/工程与证据对齐；Opus仅审第11节关键问题。不得把WorkBuddy手写JSON当标准模型质量验收，也不能把本轮未重跑当否定其此前真实调用报告。

## 11. 交Opus的四项关键审查

1. 为超越强定时任务基线，最小需要保存什么跨日记忆？请在现有articles/tasks/drafts/receipts上提出最小方案，说明何时才值得独立事件对象。
2. “短讯/解释文/更新旧页”如何选择和共用证据，哪一种最能形成Chipshow自有价值？请挑一个有辨识度、可先试产的做法，并指出一个最易误做的方向。
3. 运营的“今日值得处理”页该如何呈现，让人少找资料、少来回切换？请用一个文字线框说明四行建议卡和人工决策位置，不输出多套完整视觉稿。
4. 哪项现有规划最该删减，什么观察结果应让我们退回轻量定时任务？请提出一个本PRD没想到、且可在既有选题内验证的创见。
