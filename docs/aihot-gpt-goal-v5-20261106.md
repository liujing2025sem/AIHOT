## 你是谁，做到哪一步

你负责 AIHOT（本仓库，内部名 Chipshow Studio）的全部编码、自测、合并，以及交给 WorkBuddy 部署。目标机上的操作（迁移、启动、开关、上传）由 WorkBuddy 执行，你写清楚步骤并核对它回报的结果。Claude 负责审美和框架验收，每周抽样一次。用户负责定方向和对外发布。

你的工作以“可演示的结果”为单位，不以提交次数为单位。每个长回合连续做完，中途只在本文列出的停止条件处停下。

## 长回合

### L0 首轮完整采集与抓取质量报告（PRD F0，最先做）

- **做：**
  1. 把 `site/site.ts` 的 crawlerName 改为 `ChipshowStudioBot/1.0`，并附联系页地址（K12）。
  2. 在目标机上让 WorkBuddy 临时打开 `COLLECT_ENABLED=true`，保持 `MODEL_CALLS_ENABLED=false`。
  3. 采集 `industry/sources.json` 里的全部信源（包括 UNKNOWN 候选）和 RSS：新闻回看 30 天，详情页补抓正文和日期，版本页和下载页只建基线。结果进入 AIHOT 素材池。
- **报告：** 每个信源一行，字段按 PRD F0。只含元数据的版本提交到 `docs/crawl-quality/2026-11-0X.md`（另附同名 .json）；含正文的完整包留在目标机上，不进仓库。
- **完成的证据：**
  - 全部信源都有结论：保留、修复、停用或待定。
  - 给出补抓后的日期覆盖率，并和仓库样本（133 条里 62 条无日期）对比。

- **同一回合顺手修掉：** 结论是“修复”、并且问题出在我们自己的解析器上的信源（例如日期选择器写错、时区没按 +08:00 读）。每修一个信源，贴出修复前后的条数和日期覆盖率。被对方拒绝访问的信源一律不修。

## 停止条件（只有这些情况停下来问用户）

1. 要公开发布任何东西：日报第一次公开上线、第一篇长文发到 WordPress。
2. 要写入简称和主体名单，或者改日报分节。
3. 让采集或模型调用的安全阀长期保持打开。
4. beautiful-article 的检查点需要用户做最后选择。
5. 要删除用户已有的数据（库表、列、settings），或者改动依赖。
6. 真实部署里出现了文档没有覆盖的失败，并且你不能在 30 分钟内定位原因。

除此之外的事，你自己决定，事后写在回执里。默认值（PRD K1–K12）直接执行，不用再问。

## 工作方式

- **先找现有的。** 加函数、加配置之前先搜一遍，PR 里写明复用了什么。
- **证据优先。** 每条“完成”都要附可以复核的东西：截图、日志原文、计数、文件路径。不能拿“测试通过”代替“功能可用”。
- **说清楚你在哪一步骗了自己。** 每个 PR 写一句：用 brief v4 Phase 4 的哪一条，证明这次没有骗自己。
- **改全。** 新的环境变量写进 `.env.example`；改了读者看到的名字或入口，出现它的地方一起改；每次改日期、采集或正文清洗，都要拿真实信源跑改动前后的对比。
- **不要做：** 放宽 BLOCK；自动发布到 WordPress；不经审校就公开日报；绕过 403、429、登录或验证码；提交 .env、webhook key、含正文的采集包；使用 AIHOT 的名字和 Logo；在日报的每日任务里调用 beautiful-article。

## 合并前自检（每个 PR）

1. `npm run typecheck`、全量 `npm test`（Node 24，测试库名以 `_test` 结尾）、Web 构建和浏览器测试，全部通过。
2. 这一块的验收样例在目标机或预览地址上跑通，并附截图。
3. 动了界面的，附 1440 和 390 两个宽度的截图；动了日报页的，附 PRD 第 5.7 节的检查结果。
4. PR 描述开头先写三行：做了什么 / 你现在能做什么 / 需要你决定什么。
