# AIHOT 命题采编规格 v1：运营出题，AIHOT 备料

> 日期：2026-11-08。本文是执行计划 v2 的补充，属于 S1-2 的实现规格。冲突时以 `docs/LIVE.md` 为准。原型：`docs/prototype/pitch-desk.html`。

## 0. 结论

- **现在有入口，没有“辅助”。** PR #11（CI 已通过，待合并）里，运营可以在问题地图的某一题上点“发起人工选题”，生成一张人工卡（触发类型 M）。MiP 首篇就是这样做出来的。但之后的事全靠手：运营要自己去素材页按**标题**搜索（`studio.ts` 只对标题做 ILIKE，每页 30 条），逐条绑定，再一次性生成全文。
- **缺的四样：** ①不能直接写一句题目，必须先进问题地图；②系统不会按题目去库里找证据（不搜正文、不排相关度、不给摘句）；③不检查官网是否已有同题页面；④没有“先备料、后成稿”，方向不对就白生成一篇。
- **怎么补：** 在 PR #11 的人工卡上加一个“备料”步骤。运营写一句题目，worker 用一次便宜的模型调用，加上库内检索，出一张中文备料卡；运营花 3 分钟确认后，才生成英文全文。数据全部复用现有的问题、人工卡、素材、任务和审稿流程，不新建数据表。
- **放在哪：** 执行计划 v2 的 S1-2（尺寸指南升级稿）就是它的第一个真实用例；按新闻搜索补采放到 S2。

## 1. 现状核对

| 能力 | main | PR #11 | 缺口 |
|---|---|---|---|
| 运营给题 | 问题地图可手工建题、导入 | 题目上“发起人工选题”，生成人工卡（M） | 不能直接写题；询盘原话没有脱敏步骤 |
| 找证据 | 素材页按标题搜索，可筛信源和质量 | 人工卡跳到素材页绑定 | 不搜正文、不排序、不给摘句；不按题补采 |
| 防撞题 | 问题地图有 `existing_url` 字段 | 卡片显示“已有页面” | 没有页面登记表；不会提示“该升级旧页” |
| 先备料再成稿 | 无 | 无 | 一次生成全文 |
| 标题候选与工程确认 | 无 | 无 | 计划 v2 的 D-11 和钩子规则还没有落点 |

**核对 Gemini 的说法：** “PRD 的 F05/F08”在仓库文档和 GPT 11-07 的 PRD/SPEC 里都找不到这两个编号；`studio_tasks` 没有 `payload` 字段，实际是 `request jsonb`（已经用 `request.articles[].binding` 绑定多条素材）。

## 2. 用户故事与时间预算

运营拿到一句客户问题或一个想写的方向，1 分钟内交给系统；3 分钟看完备料卡并做选择；工程师用 1 分钟回答不超过 3 道中文单选题（可以异步）；然后进入原有的审稿和 WP 草稿流程。备料不合格（证据不够），系统直接说清楚，不生成全文。

## 3. 四步流程

### 第一步：写题（运营，≤1 分钟）

Studio 顶栏加 **“+ 命题”**，问题地图每题保留 PR #11 的“发起人工选题”。表单只有四项：

1. **问题或命题**（必填，中英文都行，可以直接粘贴询盘原话）。保存前自动把邮箱、电话、网址里的客户域名、人名后缀替换成占位符，并显示给运营确认。
2. **产出类型**：升级已有页 / 新长文 / 短文章。可以不选，由备料卡建议。
3. **已有页面 URL**：选“升级已有页”时必填。
4. **线索链接**：0–3 个（原厂页面、PDF）。照片 v1 不上传，正文里留占位，由运营在 WP 里放图。

提交后：在问题地图里新建一题（来源标记“命题”，以后进入 30 问和页面登记），并按 PR #11 生成人工卡，状态显示“备料中”。

### 第二步：备料（worker，约 30–90 秒）

模型只在 worker 里调用（AGENTS.md）。备料任务做六件事：

1. **抽关键词：** 一次 Flash 调用，给出英文搜索意图版的题目、5–10 个中英关键词、涉及的实体（型号、标准、厂商）。
2. **库内检索，不受短讯 14/30 天窗口限制：** 在素材的标题和正文里按关键词匹配，按“命中关键词数 → 一手来源 → 日期”排序，取前 8 条，每条给出命中句、原文日期和版本。素材规模只有几千条，v1 用 ILIKE 即可，不加索引；同一个函数也替换素材页现在的“只搜标题”。
3. **抓线索链接：** 运营给的链接走现有的素材抽取（`studio.material.extract`）进素材池，标为“运营提供”。
4. **防撞题：** 题目带 URL 时，抓取该页正文，作为“已有页面正文”绑定（复用卡片的证据清单）；不带 URL 时，在问题地图的 `existing_url` 和页面登记表里找相近页面，找到就建议“升级已有页”。同一问题已有进行中的任务，就提示接着做，不另开。
5. **大纲和证据对照：** 第二次 Flash 调用。输出 4–7 节大纲，每节标出靠哪条素材的哪句话撑住；撑不住的标为“缺证据”，并给出处理方式：补链接、问工程师，或删掉这一节。
6. **标题和工程确认卡：** 升级页和长文给 3 个搜索意图标题（关键词在前，≤60 字符）和 3 个社媒钩子；短文章给 3 个钩子标题。每个都标出事实锚点。需要工程判断的“缺证据”节生成 ≤3 道中文单选题；每题第一个选项是**保守写法**（不写具体数字，只写“以型号图纸为准”之类），其余是真实可选的做法，最后一项是“其他，请写明”。

最后过一遍私有黑名单（G2）：大纲里命中禁止项的节直接删掉，命中待确认项的节转成确认题。

**备料不合格的情况：** 相关素材少于 2 条，且运营没给链接时，备料卡写明“证据不足”，给出两个选择：补链接，或改成短文章。这时不生成全文。按新闻搜索补采放到 S2。

### 第三步：确认（运营 ≤3 分钟；工程师 1 分钟，可异步）

备料卡（中文）上，运营做四件事：勾选要用的素材；选一个标题；删改大纲的节；确认产出类型。

工程确认卡做成一段可以复制的文字，由运营发到企业微信，工程师回“1A 2B 3A”，运营录入答案并写上工程师名字。工程师没回复时，运营可以点“用保守写法先出稿”：所有确认题按选项 A 处理，正文不出现对应的数字。**运营不能代替工程师选 B 或 C。**

### 第四步：成稿（沿用原流程）

点“生成英文稿”后，按现有方式建任务：`request.articles` 放勾选的素材，新增 `request.pitch`（题目、类型、URL、选定标题、大纲、工程答案和答题人）。成稿调用沿用现有的 Flash、回执和编辑门；之后的审稿（必须确认 ≤8 条）、批准和 WP 草稿推送都按计划 v2 不变。升级稿推成 `[UPDATE]` 草稿，并附“改了什么”清单。署名 Reviewed by Chipshow Engineering Team。

## 4. 数据与代码映射（不新建表）

| 用途 | 复用 | 新增 |
|---|---|---|
| 题目 | 问题地图（questions） | 来源字段“命题”；脱敏后的原话 |
| 卡片与状态 | PR #11 的人工卡（document jsonb） | `document.prep`：关键词、素材候选、大纲、标题、确认题、答案；状态加“备料中 / 备料完成 / 证据不足” |
| 素材 | articles、`studio.material.extract` | 正文检索函数（替换只搜标题） |
| 任务 | studio_tasks（`request jsonb`） | `request.pitch` |
| 模型 | providers/llm、receipts | worker 队列 `studio.prep`；两段提示词放 `industry/prompts/` |
| 审稿与发布 | 编辑门、审稿、导出、WP 推送（S1-1） | 无 |

## 5. 护栏（控制在推进工作的 1/5 以内）

- **询盘脱敏：** 邮箱、电话、人名、公司名在保存和送模型之前替换；替换结果给运营确认。
- **无证据不成稿：** 选中的素材少于 2 条，且没有已有页面正文时，“生成英文稿”按钮不可用。
- **公司事实：** 黑名单在备料和成稿两处都检查（G2）。
- **工程确认：** 保守写法是默认；运营不能替工程师选择。
- **不重复：** 同一问题有进行中的任务就接着做；同一 URL 不同时开两份升级稿。

## 6. v1 不做

照片上传；按新闻搜索补采（S2）；向量检索；页面登记表的界面（S2-2，v1 只读问题地图的 `existing_url`）；企业微信机器人；给销售的定制版。

## 7. 验收样例

1. **尺寸指南升级：** 题目“户外 LED 招牌尺寸怎么定，询价前要准备什么”，类型选升级，填入尺寸指南的 URL。2 分钟内出备料卡：已有页面正文已绑定，库内素材 ≥3 条且带命中句，大纲每节有出处或“缺证据”，3 个标题，≤3 道确认题。运营 3 分钟内确认，WP 草稿箱里出现 `[UPDATE]` 草稿和改动清单。
2. **询盘原话带邮箱：** 保存前邮箱被替换成占位符，送给模型的文本里也没有。
3. **重复题：** 再提一次 MiP 的题，提示已有进行中的任务，不另开。
4. **证据不足：** 一个库里没有素材、也没给链接的题，备料卡写“证据不足”，生成按钮不可用。
5. **工程师未回复：** 点“用保守写法先出稿”后，正文里不出现确认题涉及的数字。

## 8. 对 Gemini 方案的修正

| Gemini 的写法 | 修正 | 原因 |
|---|---|---|
| 15 秒出备料卡 | 30–90 秒，worker 异步，页面显示进度 | 模型只能在 worker 里调用；15 秒不现实 |
| 所有类型都出 3 个钩子标题 | 长文和升级页用搜索意图标题，钩子只用于社媒 | D-03、D-04 |
| 单选题选项含明显错误的做法 | 选项都是真实做法，第一项是保守写法 | 带陷阱选项的题，工程师一眼看穿，等于没问 |
| 工程师没空，运营直接选 A 先出稿 | 保留，但只能选保守写法，正文不出现对应数字 | 运营不能替工程师下技术判断 |
| 外部即时定向抓取 | v1 只抓运营给的链接；新闻搜索补采放到 S2 | 先用现成的抽取，少一个运行部件 |
| 上传现场照片 | v1 不做，正文留占位 | 减少文件存储和推送工作 |
| 用 `payload` 字段 | 实际是 `request jsonb` | 以代码为准 |
| 未提询盘隐私 | 增加脱敏 | 询盘含客户信息，仓库是公开的，模型调用也会外发 |
